# Architecture

## 1. Schema, locking, transactions

Two tables. `inventory` carries the counters (`total_stock`, `reserved_stock`), `reservations` is the
state machine for each hold (`active` → `confirmed` | `expired`). The counters are derived data kept
denormalised on purpose: a reservation is then one statement instead of an aggregate, and the row
lock Postgres takes for that statement is the mutex everyone queues on.

Overselling is prevented by a single conditional update, not by a read-then-write in Go:

```sql
UPDATE inventory
   SET reserved_stock = reserved_stock + $2, updated_at = now()
 WHERE item_id = $1 AND $2 > 0 AND total_stock - reserved_stock >= $2
RETURNING reserved_stock;
```

The comparison happens inside the locked row, so two concurrent buyers cannot both pass a check that
each read separately. Zero rows is not an error but an outcome, and it means two different things, so
the same transaction asks `SELECT EXISTS` which one it got: `ITEM_NOT_FOUND` or `INSUFFICIENT_STOCK`.
`$2 > 0` belongs in the SQL because the `quantity` CHECK on `reservations` guards the row being
inserted, not this arithmetic: without it, a negative quantity would add stock back.

Three `CHECK` constraints (`total_stock >= 0`, `reserved_stock >= 0`, `reserved_stock <= total_stock`)
are the last defence. If a future code path is wrong, it fails with a constraint violation instead of
quietly writing a bad balance, which is the difference between an incident and a corrupt table.

Isolation is `READ COMMITTED`, pinned explicitly. Serialisable isolation would abort most of a
flash-sale burst on read-write dependency conflicts and turn the retry rate into the throughput
limit, while the contention here is a single row per item that row locks already serialise. Only
`40001` and `40P01` are retried, five attempts with jitter; `40003` (statement completion unknown)
is never retried, because reserving twice is exactly the bug the service exists to avoid.

Lock order is inventory → reservations on the reserve path and reservations → inventory on confirm,
so the two paths can still deadlock under load. That is handled as a retry rather than prevented with
an advisory protocol, and the expiry sweep takes locks in the same order as confirm.

Deadlines are generated by the database (`now() + make_interval`), and reservation ids come from a
sequence in the same insert. With ten replicas, an application-computed deadline means the host that
answered the request sets the clock for that reservation.

The sweep is one transaction:

```sql
SELECT pg_try_advisory_xact_lock(hashtext('inventory_reaper'));
-- pick due rows FOR UPDATE SKIP LOCKED, LIMIT 500
UPDATE reservations SET status = 'expired' WHERE reservation_id = $1 AND status = 'active';
UPDATE inventory SET reserved_stock = reserved_stock - $2 WHERE item_id = $1 AND reserved_stock >= $2;
```

Splitting it in two would leak `reserved_stock` permanently on a crash between the halves. The
`status = 'active'` guard is what makes a confirm racing the sweep safe: whichever statement flips the
row first wins, the other affects zero rows and returns nothing. The advisory lock makes N replicas do
one unit of work per tick; `SKIP LOCKED` stops two sweeps blocking each other; the batch limit stops
one huge backlog from holding the transaction open past the statement timeout. The partial index on
`expires_at WHERE status = 'active'` keeps the pick off the dead rows.

`reserved_stock` is derived, so it is reconciled rather than trusted: a view compares it against the
live reservation totals every twelve ticks and logs any item that disagrees. Drift is a finding, not
something to overwrite — if they differ, a write path is wrong and repairing the number would hide it.

Gin routes are grouped under `/api/v1/inventory` with two middlewares, request id and recovery.
Handlers bind, call the service, and map a domain error to a status through one table in `handler.go`;
the service validates and owns the transaction policy; SQL lives only in the repository. Write phases
run on `context.WithoutCancel(ctx)` with their own budget, so a buyer closing the connection cannot
roll back a hold the database already granted. Shutdown is: readiness flips to 503, then
`server.Shutdown` with a budget larger than the statement timeout, then cancel the reaper and wait for
it, then close the pool. Any other order drops in-flight commits or kills a live transaction.

## 2. Ten instances

Nothing in the request path is stateful, so scaling out does not break correctness: two instances
holding no session both resolve their contention inside Postgres. What breaks is throughput. One hot
item is one row, and every writer across all ten instances serialises on that row's lock. Instance
count buys headroom for the *other* items, not for the one everyone is fighting over; the ceiling is
roughly `1 / (lock hold time)` per item. Connection count is the second wall: 10 × 25 pool is 250
connections against Postgres's default 100, so either the pool shrinks per instance or a pgbouncer
goes in front. The reaper degrades to nine idle replicas by design.

Failure modes worth naming: the database is the single point of truth and of failure, so `healthz`
pinging it takes the whole fleet out of rotation during a blip (deliberate — a node that cannot reach
Postgres cannot reserve either); an instance killed mid-transaction leaves a commit or a rollback and
nothing in between; the sweep is restart-safe because its predicate is `expires_at <= now()`, so a
hold that lapsed while every replica was down is caught on the next tick.

To actually scale one item, move the counter off the single row. Shard it: N stock rows per item, each
reserve picks one at random, and "available" is the sum, which multiplies the lock targets by N and
turns a hot row into a warm one. Or invert the concurrency: route all writes for one item through one
owner (a queue keyed by `item_id`, or one leader per shard) so contention becomes ordering, and let
Postgres stay the durable ledger rather than the lock manager. Reads then go to replicas with an
staleness budget, expiry becomes a delay queue instead of a poll, confirmations go out through an
outbox, and a retried `POST /reserve` carries a client-generated idempotency token with a unique index
so a timeout retry returns the original hold instead of a second one.

## 3. Trade-offs

Denormalised counters buy O(1) stock reads and atomic reserve, and cost a number that can sit up to
one sweep interval above the live total. The alternative, aggregating reservations on every read, is
correct and slower, and would not have fit the time box. I kept the stale window and made it
observable: the view, the reconcile log line, and a note in the dashboard.

Expiry is polled every five seconds rather than scheduled per reservation, so a released hold can
remain invisible for up to one interval. It needs no extra process and no second clock. Reservation
ids from a sequence keep the primary key small and ordered, and are enumerable, which is fine for an
assignment but would want an unguessable token plus auth in a real system. There is no auth, no
per-user hold limit, and no order or price model; the brief stops at confirmation.

On the frontend: no component library and hand-written CSS to keep the build to four dependencies,
polling instead of a socket, and the tracked list in `localStorage` so it survives a reload. The
countdown reads the database-issued `expires_at`, so a refreshed page shows the true remaining time
rather than restarting five minutes. Validation is duplicated on purpose: the form rejects nonsense for
feedback, the SQL is the only thing that decides. The database-backed tests skip when no Postgres is
reachable instead of failing, which keeps `go test ./...` usable anywhere but lets a fresh clone run a
partially skipped suite; that is documented in the README rather than hidden.

**AI use.** I used an AI assistant for design review and drafting, and one of its suggestions was
wrong in a way that would have shipped silently: cleaning up expired holds as two transactions, one to
mark the rows expired and a second to return the units. A crash between them leaves `reserved_stock`
permanently inflated, and nothing repairs it later because the rows already say `expired`, so the
sweep skips them. I put both halves in one transaction and added the `status = 'active'` guard on the
update, which also settles the confirm-versus-expire race in the same statement. The review pass
caught two smaller ones: a generated schema that created an `idempotency_key` column and a matching
unique index that no code path ever wrote (dead weight pretending to be a feature, so the column went
rather than a fake implementation), and an early draft that computed `expires_at` in Go, which makes
each replica's host clock authoritative for the reservations it served. What the tool did not supply:
the final decisions, the review above, and the stress tests that prove the invariants rather than
asserting the design sounds plausible.
